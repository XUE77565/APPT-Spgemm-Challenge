## 第 0 章 · 一句话回答你的问题

**问:你做的这些是不是大部分都是工程优化?Ocean 是不是工程上非常完备?**

**答:是的,两点都对。** 我这两晚的优化,按性质分:

| 类别 | 占比 | 例子 |
|---|---|---|
| **纯工程**(不改算法,只让同样的算法跑得快) | ~70% | warp-per-row 批量、warp 聚合原子、count kernel 重映射、blockDim 调优、64 位溢出修复 |
| **数学/统计修复**(公式错了,修正) | ~15% | MinHash 估计器(Jensen 不等式)——这是真发现,但属于"把我们自己的公式修对" |
| **算法结构**(改变"怎么算") | ~15% | dense 窗口路径、行级重试、heavy 全局表(且后两者是对 Ocean 已有机制的效仿) |

而 **Ocean 的代码是一个工程完备度极高的项目**:它对每一种矩阵形态(超稀疏/稀疏/稠密/重行/离群行)
都有专门优化的 kernel 和自动分流器,连"值该放共享内存还是全局内存"都做了混合设计。
我们昨晚追上的部分,本质上是在补 Ocean 团队已经做过的工程课。

**但这也正是论文的正确叙事**(详见第 6 章):
我们的贡献在**算法/架构层**——hash 与 merge 两个家族间的自适应调度、merge 的列值域切分、
MinHash 估计的数学修正;工程追平只是让这些算法主张**变得可测量**。不要把工程数字本身
当成论文的创新点,评审一眼就能看出来。

## 第 1 章 · 背景五分钟:我们在算什么

**SpGEMM** = 稀疏矩阵 × 稀疏矩阵。挑战赛要求算 C = A×A 和 C = A×Aᵀ,矩阵来自电路仿真、
电网、有限元等真实工程,100~337 个,在 NVIDIA H100 GPU 上比谁快。

**稀疏矩阵** = 绝大多数元素是 0 的矩阵,只存非零元素。存储格式 **CSR**(按行压缩):
每行存"这一行有哪些列有非零值 + 值是多少"。

**乘法难在哪**:C 的第 i 行 = A 的第 i 行引用的每一行 B(这里 B=A)拼接起来再**同列相加**。
比如 A 的第 i 行引用了 500 行,每行平均 100 个非零 → 拼出 5 万个"中间积",
其中大量列号重复(比如列 7 出现了 200 次)→ 要把这 200 个数加成一个。
**去重合并这一步占了总时间的 70-80%,是整个问题的核心。**

## 第 2 章 · 去重的两大门派(我们和 Ocean 都属于此)

**hash 派**(我们和 Ocean 的主力):
像查字典——开一张表,列号经过一个**散列函数**(把列号搅乱成一个准随机的槽位号)决定放哪。
- 新列号 → 用 **atomicCAS**(原子比较交换:试探这个槽是不是空的,是就占住)插入;
- 已存在的列号 → 用 **atomicAdd**(原子加:往那个格子里加数,保证多个人同时加不丢)累加。
字典放在 GPU 的**共享内存(SMEM)**里特别快——这是 GPU 每个计算单元自带的小高速缓存。

**merge 派**(我们的另一条路):每一行 B 本身列号有序,像把几摞已排好的扑克牌**归并**成一副,
归并过程中同列号自然相遇相加,输出天然有序、完全不用排序,也不用散列。
弱点:归并的"挑最小"步骤难并行。

**自动调度(dispatcher)**:我们的 Auto 像一个分诊台——看矩阵的几个特征(行数、行长、
乘积量),决定这个矩阵走 hash 还是 merge。Ocean 没有 merge,它是在 hash 内部
按"平均每行乘积数"切换不同工作流(原理相同,层次不同)。

## 第 3 章 · GPU 性能的四个入门概念(看懂优化的钥匙)

1. **共享内存 vs 全局内存**:SMEM 是每个 GPU 流处理器(SM)的私有超快缓存(~228KB/SM),
   访问比全局内存(显存,80GB)快 5-20 倍。表放 SMEM = 快,但装不下大的。
2. **占用率(occupancy)**:一个 SM 同时住几个计算块(CTA)。住得越满,等待内存的
   时间越能被别的块的工作填满。我们的 dense v1 起初只住 1 块(25% 占用)→
   把每块线程数 256→512,同样内存住满 → 快 1 倍。**这是纯工程,但非常值钱。**
3. **原子操作争用(contention)**:atomicAdd 像**只能一个人过的独木桥**——1000 个线程
   同时加同一个格子,就得排队。我们遇到过"337 万行 × 12 个计数器"全挤一座桥 →
   用"warp 聚合":同一小组里目的地相同的人合并成一张票,一次过桥(5.9→0.24ms)。
4. **固定开销/延迟 vs 吞吐**:小矩阵的总时间被"启动 kernel 的固定延迟"主导
   (每次 ~10 微秒 × 几十次启动),大矩阵被"吞吐"(每秒能处理多少积)主导。
   bcsstk30(4ms 的小活)对固定延迟极其敏感——这就是它反而退步的原因(见 4.6)。

## 第 4 章 · 每一步优化,用大白话重讲一遍

### 4.1 MinHash 估计器数学修复(我们最重要的单项,15% 的"真发现")
问题:去重前要先估计"每行有多少个不同的列号"(决定表开多大、缓存开多大)。
我们的估计公式用了"每格最小值的**倒数之和**"——数学上这叫**调和平均**,
而被 1/x 这种凸函数坑了(**Jensen 不等式**:倒数的平均 ≥ 平均的倒数),
系统性**高估** 2-5 倍(个别矩阵 20 倍)。表开太大 → 白占内存、白初始化。
修复:改用"最小值的**算术平均**"——公式变一行,数学上无偏。
> 类比:估算收费站车流量,原来数"每条道最快的那辆车的车速倒数"(被慢车拖累,估高),
> 改成"每条道平均车距"(准了)。

### 4.2 64 位溢出(纯 bug 修复,但差点烧了 GPU)
所有计数累加用 32 位整数,超过 21 亿会**绕成负数** → 分配"负数个字节" = 天文数字
→ GPU 驱动卡死(术语:GPU wedge,需要管理员权限重启)。某矩阵真实乘积数 147 亿,炸了。
修复:全部换 64 位 + 分配前检查。**这是安全修复,不是性能优化。**

### 4.3 行级重试(向 Ocean 学的机制)
概率估计总有看走眼的行(估 100,实际 120)。旧行为:一行看走眼 → **整个矩阵推倒重来**
(退到慢的 merge 路径),太狠。新行为:把看走眼的行记下来,单独用"精确上界"
(乘积总数一定 ≥ 不同列数,这是数学保证)重新跑这几行。
> 类比:考试有一题超纲,原来全班重考,现在只让几个学生补考。

### 4.4 warp-per-row 批量 kernel(纯工程,治 333SP 类)
GPU 的最小作战单位是 **warp**(32 个线程齐步走)。原来一行矩阵要派一个 256 人的**营**(CTA)
去处理,而 333SP 平均每行只有 6 个乘积——一个营伺候 6 个数,纯属浪费。
改成:一个 **warp(32 人班)**负责一行,一个营同时带 8 个班干 8 行。
accumulate 从 22ms → 6.5ms。

### 4.5 dense 累积器 + 窗口(算法味道最浓的一步)
发现:像 exdata_1/TSOPF 这种"输出 25-47% 都是非零"的矩阵,开散列表纯属浪费
(查 100 次有 75 次落空)。改用**直接寻址**:第 j 列就放数组第 j 格,零查找零冲突,
只有纯加法。n 大于 SMEM 装不下的(TSOPF n=28216)→ 按列切成窗口,一个窗口一个窗口过
(窗口按序处理,输出天然有序,免排序)。这是从 Ocean 的 denseNumericIter 得到的启发,
但我们给出了自己的门控条件(输出密度 ≥ 15%)。

### 4.6 bcsstk30 为什么反而退步了(工程优化的零和陷阱)
bcsstk30 是个 4ms 的小活。为了大矩阵加的每个"新环节"(count 阶段 +0.05ms、
重试管线 +0.74ms)在大矩阵上是零头,在小矩阵上就是 20-30% 的退步。
试过"小矩阵用松估计免重试"——结果省了重试、赔了排序,**零和**(EXPAND 扫描数据在文档 07)。
结论:小矩阵要追平,必须把重试做成"零宿主往返"(Ocean 在 kernel 内部完成,我们还在宿主端倒手)。

## 第 5 章 · Ocean 到底强在哪(诚实的敬意)

读它的源码后我确认,它的工程完备度体现在**每一层都有针对性设计**:
- **矩阵内分流器**:先算每行精确乘积数,平均 ≤64 → 免估计的超稀疏工作流;
  平均大 → HLL 估计 + hash;还有 FAT(超胖矩阵)、离群行(outlier)专门通道。
- **kernel 形态精细**:小行用"每 CTA 多行 × 每行 16/32 线程",甚至 4 线程的 sub-warp 变体;
  表的键放共享内存、值放全局内存池(HYBRID_HASHMAP)。
- **负载均衡**:按乘积前缀和切分工作,不是按行数。
- 反过来说:它的**算法层没有** merge 家族、没有跨家族调度——这是我们真正的差异点。

## 第 6 章 · 这对论文意味着什么(定位建议)

1. **主张应该锚在算法/架构层**:①hash/merge 双家族自适应调度(含带状阵 35× 的 merge 优势类别)
   ②列值域切分的 warp merge ③MinHash 估计的数学修正(可推导、可复现)
   ④dense 窗口的密度门控。工程数字(追平 Ocean)是**验证**,不是贡献。
2. **诚实呈现工程对比**:我们不回避"工程完备度不及 Ocean"——反着用:
   "在工程投入远小于 SOTA 的情况下,靠算法层设计达到 X"是合理叙事。
3. **DATE 的 EDA 框架**是加成:套件本身是电路仿真矩阵,贴近会议受众。

## 第 7 章 · 当前战绩与还差什么(随进度更新)

干净直测(compute-only,2026-08-26 Step3 后):
```
3Dspectralwave2 0.88×胜 | pwtk 1.31× | exdata 1.41× | 333SP 1.56× | bcsstk30 1.61× | TSOPF 1.72×
```
干净基准(ocean337v2,337 阵全量重跑)进行中——早期信号:vsp_* 船体系列 ~2.4×,
是下一个 TSOPF 式的目标类。剩余瓶颈的本质(预告):
- **小矩阵**:固定延迟(重试的宿主往返、多阶段启动)——工程问题;
- **vsp/重行类**:中尺寸表 × 高重复的原子加链——可能需要 dense 窗口门控放宽或表分片;
- **333SP 类**:批量 kernel 内循环的最后一程(6.5 vs 4.1ms)——微调工程。
