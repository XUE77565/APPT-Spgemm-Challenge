## 0. 先搞懂几个最基础的概念

| 词 | 通俗解释 |
|---|---|
| **GPU / kernel** | GPU 是算力很强的芯片。一个 **kernel** = 一段丢给 GPU 去并行跑的函数(一次能启动成千上万个线程一起算)。 |
| **h2d / d2h** | **h**ost **to** **d**evice(h2d)= 把数据从 CPU(主机)搬到 GPU;d2h = 反过来搬回来。计算前要先 h2d 把矩阵搬进去,算完 d2h 把结果搬出来。 |
| **PCIe** | CPU 和 GPU 之间那条数据通道(像一根很粗的数据线)。搬数据就走这条,有固定上限速度。 |
| **pinned memory(锁页内存)** | 见下面第 1 节,这是本页重点。 |
| **wall-clock / compute-only** | wall-clock = 从程序开始到结束的真实总时间(含搬运);compute-only = 只算 GPU 真正计算那部分(扣掉搬运)。论文对比通常用 compute-only(公平)。 |
| **ms(毫秒)** | 1 秒 = 1000 ms。0.18ms = 万分之 1.8 秒,非常快。 |

## 1. 重点详解:h2d/d2h + pinned 池化(这是"一开始"做的优化,也是图的主角)

### 1.1 问题:每次搬数据都要"办手续",很慢

数据要从 CPU 搬到 GPU(h2d),最朴素的做法是:每次搬之前,临时申请一块**特殊内存**用来搬,搬完就释放。这个"申请特殊内存"的动作叫 `cudaMallocHost`,本质是**把内存"锁页"(pin)**——告诉操作系统"这块内存你别动,固定住,好让 GPU 直接来读"。

问题:**锁页这个动作本身很贵**(它是一次系统调用,要操作系统介入改页表)。如果一次计算要来回搬很多次数据,每次都锁一次、解锁一次(`cudaFreeHost`),这些"办手续"的时间就堆积成大头。

> **生活类比:** 就像你每次寄快递都要先跑一趟邮局排队办手续(pin),寄完再跑一趟注销(unpin)。寄 100 次就跑 200 趟邮局——快递本身不慢,慢的是来回办手续。

### 1.2 两个关键认知:为什么"锁页" + "池化"都重要

**(a) 为什么要锁页(pinned)?**
- 普通内存(没锁的,叫 pageable)GPU **不能直接读**,操作系统得先帮你中转一次(偷偷复制到一块锁页区再搬)→ 多一次复制,而且**没法异步**(得卡在那等)。
- 锁页内存(pinned)GPU **能直接读**(DMA,直接内存访问),走 PCIe **满速**,还能**异步**(GPU 搬数据时 CPU 可以同时干别的)。
- 所以:**用锁页内存搬运,本身就更快**。

**(b) 为什么要池化(pool)?**
- 即使知道锁页好,也不能每次搬运都重新 `cudaMallocHost` 锁一遍(手续贵)。
- **池化 = 开工前一次性申请并锁好一大批锁页缓冲(buffer),放进一个"池子";之后每次搬运,直接从池子里拿一个用,用完还回去,不用再办手续。**
- 还回去的时候**不释放**(只是标记"可复用"),所以**循环里 0 次锁页系统调用**。

> **生活类比(续):** 池化 = 你直接办了一张"月卡",邮局给你留 10 个固定箱子随时用,你寄完把空箱子放回去就行,再也不用排队办手续了。

### 1.3 图里两块对比(对应 `fig/h2d_d2h_pool.png` 和详解页 `fig/pinned_pool_detail.png`)

**左块 ① Without pool(没池化,红):** 每次搬运 = `cudaMallocHost`(锁页,慢)→ 搬 → `cudaFreeHost`(解锁)。循环 N 次 = N×2 次昂贵系统调用,而且用的是 pageable 内存(还得被中转)。

**右块 ② Pinned pool(我们的,青):** 开工前先建池子(allocate & page-lock **ONCE**,只锁一次);每次搬运 = `pool.get()`(从池子拿一个,O(1),没系统调用)→ 搬(DMA 满速 + 异步)→ `pool.return()`(还回去,no-op)。循环里 **0 次锁页**。

### 1.4 效果(实测)

| 矩阵 | 优化前 wall-clock | 优化后 |
|---|---|---|
| bcsstk30 | 58.7 ms | **9.2 ms** |
| bcsstk17 | 9.4 ms | 1.9 ms |
| bcsstk11 | 1.84 ms | 0.91 ms |

> **一句话:把"每次搬数据都要现办手续"改成"开工前一次办好、反复用",省掉了几乎全部搬运开销。**

## 2. 上面那 4 个小卡片:计算的四个阶段(compute pipeline)

数据搬进 GPU 后,真正的计算分四步,每步我们都做了优化。这 4 个卡片就是讲这四步。

### ① Sizing —— 先估"结果有多大",好提前分配内存

**做什么:** 算 A·A 之前,要先知道结果有多大(有多少个非零元),才能分配正好大小的内存。
- 我们用 **MinHash**(一种"估算"算法:不用精确数完,扫一眼就能估个差不多)→ 只需扫一遍 A 的行就能估。
- 对照:opSparse 这个对手要**两遍**(一遍专门数、一遍才算),我们一遍够。
- **EXPAND 2.0 → 1.5:** 估算总有误差,原来留 2 倍余量(怕估少了溢出),实测发现 1.5 倍就够安全 → 内存省了、要排的数据也少了。

**结果:** 估大小的阶段比 opSparse **快 3.5 倍**;内存多分配倍数从 3.14× 降到 2.29×。✓ KEPT(保留)

### ② Accumulate —— 真正做乘加累加(这一步是"地板",红色卡片)

**做什么:** 对结果的每一行,把所有乘积 `A[i][k]×A[j][k]` 加起来。同一列 j 可能出现很多次(dup,重复因子最高 **19×**),要**去重 + 累加**。
- 用 **hash 表**(一种"快速查找/去重"的数据结构):每个列 j 算个位置放进去,来了重复的就加到一起。
- 插入用 `atomicCAS`(占位),累加用 `atomicAdd`(加)——这俩是"原子操作",意思是**多个线程同时改同一个位置时,得一个一个排队来,不能同时写**。

**为什么是"地板"(改不动):** 热门的列 j 被轰击 ~19 次,这 19 次原子加法**必须排队**(硬件限制),没法并行。我们试了 3 种减少排队的招(read-check、打包 CAS、warp 私有表)**全部失败**——证明了这一步是结构性的、改不动的瓶颈(叫 atomic floor)。

> **生活类比:** 一个收银台(热门列),19 个人(deup)都要在这结账,只能排队——你再怎么优化队伍,收银台本身就只能一个一个来。这不是没努力,是物理极限。

✗ FLOOR(到顶,不是没做,是做不到更快)

### ③ Extract —— 把 hash 表里的结果取出来、排好序

**做什么:** 累加完,结果散在 hash 表里,得取出来、按列号排好序、写成标准格式。
- **count-sort:** 一种排序法——每个元素数"比我小的有几个"→ 算出自己该排第几 → 直接放到位。**不用同步(sync-free)**,因为每个元素独立算自己的名次。
- 实测:排"很多很小的数组"时,这种 O(n²) 的笨办法反而赢过更"高级"的 bitonic(要频繁同步)和 radix(每个小数组单独启动太贵)。
- **pack elimination(消除打包):** 之前结果散在三块内存里,搬出前要先"打包"成连续的(多了两次复制);改成一开始就分配连续的,省掉这两次复制。

**结果:** count-sort 是这步的地板(改不动);pack 省了 **0.09ms**。✓ KEPT

### ④ Launch —— 把多个小任务合并(kernel fusion)

**做什么:** GPU 每启动一个 kernel 都有固定开销(像每次叫人都得拨号等接通)。小矩阵计算量本身≈0,时间全花在"反复启动 kernel"上。
- **kernel fusion(融合):** 把几个小 kernel 合并成一个大 kernel(比如把"分桶"和"数桶"合成一个,把多次扫描合成一次单 block 扫描)→ 启动次数变少。
- first100 测试集 78% 都是小矩阵 → 这步收益面最大。

**结果:** 小矩阵 bp* 跟 cuSPARSE 的差距从 0.03–0.08ms 缩到 **0.008ms**(基本打平)。✓ KEPT
> 详解图见 `fig/launch_fusion_detail.png`:**前**= compute_bucket、bucket_count 两个独立 kernel + 2 次 D2H + 1 次 sync + thrust est/cnnz scan(各 ≈3 个 kernel)≈ **8 次 launch**;**后**= 融合的 bucket+count 1 个 kernel + 合并的 1 次 D2H + 1 次 sync + 单 block Hillis-Steele scan = **3 次 launch**。大阵保留 thrust scan(A_rows>1024 gate,不回退)。

## 3. 一句话总结(讲这页时怎么说)

> **搬运(h2d/d2h)用 pinned 池化省掉所有"办手续"开销(58.7→9.2ms);计算四步里,能优化的都做了(MinHash 估算、count-sort 排序、kernel 合并),优化不了的(累加的原子地板)我们用三个失败实验证明了它是物理极限。**

## 5. 可能被问的问题(答辩准备)

- **Q: 为什么 device pool 又关掉了?**
  A: 我们还试过把 GPU 内部也池化(device pool),但实测它让小矩阵的扫描步骤变慢 1.5–3 倍(池化内存的访问特性不如独立分配)→ 对 compute-only 口径是负优化,所以默认关掉(留个开关 `USE_DEV_POOL`)。这也是"测了不划算就回退"的方法学体现。

- **Q: 58.7→9.2ms 这么大,主要功劳是谁?**
  A: 主要就是 host pinned 池(免掉每次 h2d/d2h 的锁页系统调用);device arena 只省了 ~0.66ms(省 ~13 次 driver call)。所以大头是锁页池化。

- **Q: 为什么累加那步是地板,却还说优化完成了?**
  A: 因为地板 = 这一步理论上最快就这样了(原子排队是硬件特性,对手 Ocean 也一样),我们证明了三个能想到的提速方向都无效,所以是"做到了上限",不是"没优化"。
